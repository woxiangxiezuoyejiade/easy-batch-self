# Easy Batch 增量开发对照实验草案 v0.1

日期：2026-10-29。状态：待复核；未实施实验，不能宣称规则有效。

## 先确定任务是否确实有增量

源码搜索未发现以 NDJSON、JSON Lines 或 newline-delimited 命名的能力，这不等于能力缺失。

- FlatFileRecordReader.java:71–78 已按行输出字符串。
- JsonRecordMapper.java:70–72 已将 Record<String> 的内容转为对象，并保留 Header。
- JsonRecordReader.java:44–56 的文档描述的是 JSON 对象数组，与逐行 JSON 不同。

因此先做小型基线能力测试：两行独立对象、无末尾换行、空文件、空行、非法 JSON、指定字符集。验证 flatfile Reader＋JSON Mapper 的组合。以上是待运行测试清单，不是已经实测的结论。

若需求只是“逐行读 JSON 并映射对象”，现有组合可能足够，新增同义 Reader 的实验价值有限。可候选“为逐行 JSON 输入增加可配置的空行策略与带来源、行号的错误诊断”，但必须先确定现有组合的不足，且不要在需求中指定唯一类名、模块或实现路线。也可选择另一个经能力核查确有缺口的输入扩展。不要因预期容易出现架构违规而只挑某一任务。

## 正式执行前锁定

1. 保存完整源码副本、文件指纹，准备 Java/Maven 与依赖缓存，运行原有测试，记录既有失败；当前目录没有可识别 Git 提交，不应虚构提交号。
2. 由用户和师兄复核规则；给规则集版本与文件指纹。固定后再开始正式实验。
3. 写明任务的输入输出、字符集、空行与非法输入策略、资源所有权；这是两组共享的功能规格。
4. 预先制定验收测试和架构评价表。评分者与测试用例不要看完结果后再选择。
5. 分析候选影响范围并选规则；分析说明可能影响的职责与原因，不规定必须改哪些文件。

## 候选影响范围示例

| 职责／接口 | 为什么可能受影响 | 当前判断 |
|---|---|---|
| 文件/流读取及字符集 | 行边界、EOF、资源释放 | 主要候选 |
| JSON 映射及错误诊断 | 解析、定位错误信息 | 主要候选，需明确错误发生阶段 |
| Record / Header | 编号、来源的承载 | 检查可复用性，不预设修改公共接口 |
| core 作业调度 | 生命周期、异常和终止的集成 | 回归观察点，不能预设必须修改或绝不能修改 |
| 模块依赖与测试 | 适配归属、编译及回归 | 检查现有依赖能否支持 |

若最终任务是 Reader 扩展，001–005 通常相关；涉及空行或过滤还考虑 006。若最终仅增加 Mapper 错误诊断，Reader 生命周期规则可能不适用，应留下排除理由。规则选取在结果出现之前完成。

## 两组输入与信息隔离

- 对照组：任务需求＋共同基础项目说明。
- 实验组：完全相同内容＋人工复核并选定的规则文本。
- 本目录的教学路线、候选影响分析、实验评价材料默认仅供研究者使用，不给某一组额外阅读。如果要提供影响分析，应两组提供相同版本；另一种方案是两组都不提供。
- 规则可能自带源码证据和定位提示，这是潜在混杂。第一轮可评价“含证据的规则包整体作用”；若要分离约束文字的作用，可让两组共享相同的源码位置列表，实验组只多约束文字，或后续增加等定位信息的第三组。
- 两组从同一未修改副本起步；禁止先完成一组后把代码或对话交给另一组。研究文档也不应留在 Agent 可自由读取的共同基线里，防止对照组读到规则。

## 一致条件与运行记录

固定模型及版本、推理设置、工具权限、系统提示、预算、可用网络/依赖、时间限制、测试权限和反馈策略。记录完整输入、选择的规则 ID、输出补丁、测试日志、耗时、token 与人工介入。预算应说明输入规则占用是否计入；相同总预算下额外规则会挤占推理空间，需在解释结果时说明。

本科小规模可先做一组配对试运行排查任务和评测问题；试运行后允许调整，但调整后的正式实验使用新版本规格并重新固定。正式建议 2–3 个不同增量任务，各组至少 3 次独立运行，交替或随机执行顺序。资源不足时如实作为小样本探索，不从单次成功推断因果。

## 预设评价

| 维度 | 操作方式 |
|---|---|
| 功能完成 | 相同验收用例通过数/总数；单独列编译失败和未完成 |
| 原有行为保持 | 同一回归测试集；记录相对基线新增失败，不把原有失败归罪于 Agent |
| 模块边界 | 001 的依赖检查＋人工审查格式特判，报告违规处与证据 |
| 生命周期协作 | 003 的正常/异常资源清理检查 |
| 接口契约 | 002、004、005、006 分项检查，与模块架构分开报告 |
| 代价 | 时间、token、人工干预次数；修改文件数仅描述，不直接等于架构质量 |

每项先标记“适用/不适用”；适用项再判通过/违反/证据不足，未完成或未编译的项不得自动判通过。001、003 是本版主要架构候选，其余更多反映跨组件契约，不能将功能验收通过直接称为架构更好。相同根因避免重复计数；保留逐次结果，不只报告平均分。让不知道组别的复核者依据补丁和测试结果评分，分歧记录并复核。报告规则无收益、引入负担或收益不一致的情况。
